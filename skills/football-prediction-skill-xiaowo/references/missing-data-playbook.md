# 缺失资料与上传请求手册

资料缺失时的目标是保留可审计边界，而不是尽量填满报告。任何 Agent 都不得把常识、模型记忆、搜索摘要或传闻写成已核验事实。

## 处理顺序

1. **识别能力**：说明当前是否具备网络、网页读取、Node.js、PNG 渲染和文件写入能力。
2. **尝试检索**：仅在具备网络能力时执行；逐项记录查询词、来源 URL、访问时间和失败原因。
3. **声明缺口**：列出精确 JSON 字段或事实名称，不使用“资料不全”等笼统描述。
4. **决定状态**：可安全继续则标记 `degraded_low_confidence`；身份、截止时间或账本不可解析则标记 `failed`。
5. **请求上传**：只有完成缺口声明后，才向用户请求最小必要文件或字段。
6. **保留边界**：未取得资料前，不猜测、不补写、不把未审计内容传入模型。

## 缺口清单模板

```text
当前状态：degraded_low_confidence
缺失字段：
- evidenceLedger[].lineupStatus（双方正式首发）
- evidenceLedger[].observedAt（伤停证据观察时间）

已尝试来源：
- 赛事官方比赛页：https://…；访问成功，但尚未发布正式首发
- 主队官方公告：https://…；页面无法访问，返回 403
- 客队官方公告：宿主无网络能力，未尝试

影响：不应用首发或伤停修正；报告显示低置信并列出重算触发器。
需要上传：包含来源 URL、发布时间、观察时间和正式确认状态的首发/伤停资料。
```

## 常见缺失与处理

| 缺失项 | 是否可继续 | 处理 |
| --- | --- | --- |
| 比赛 ID、主队或客队 ID | 否 | `failed`，请求准确赛程或结构化比赛信息 |
| 开球时间或数据截止时间 | 否 | `failed`，不得判断证据是否赛前 |
| 正式首发 | 是 | 不应用首发修正，低置信并设置正式首发发布后的重算触发器 |
| 伤停证据 | 是 | 不猜测可用性，保留缺失项并降级 |
| 天气 | 是 | 不应用天气修正，记录缺失来源 |
| 市场去水数据 | 是 | 隐藏市场概率与差值，不影响模型概率栏 |
| 赛事规程 | 视情况 | 90 分钟联赛可在画像完整时继续；淘汰赛分支必须隐藏或失败 |
| PNG 渲染器 | 否 | 正式运行失败；不得只交付 `report.md` |

## 上传材料要求

- 优先请求 JSON、CSV、官方页面导出或清晰截图；说明需要的具体字段。
- 截图必须可识别来源、发布时间和内容；缺一项时只能作为待审核线索。
- 用户上传后仍要进入证据台账并执行来源、时间、主题和冲突审计。
- 不请求与比赛无关的个人信息、账户凭据或整库数据。

## 恢复运行

新资料到达后创建新证据快照，重新运行审计。若旧运行已发布，必须创建新 `runId` 并通过 `parentRunId` 建立血缘；不得回写旧报告或替换旧 PNG。
